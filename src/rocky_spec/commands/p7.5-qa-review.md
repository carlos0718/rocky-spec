### P7.5 · Revisión funcional y de QA (Three Amigos)

**Qué es esto:** en equipos reales, antes de programar una historia se hace una revisión conjunta entre quien define el negocio (Analista Funcional / Product Owner) y quien la va a probar (QA) — a esto se lo conoce como **"Three Amigos"** (el tercer amigo es quien programa). Acá Claude hace de los dos roles a la vez, revisando todo lo que se generó en P1-P7 con dos lentes distintas:

- **Lente de Analista Funcional**: ¿está completo? ¿es consistente? ¿hay ambigüedades?
- **Lente de QA**: ¿es testeable? ¿están los casos borde contemplados?

**Saltear (o hacer versión liviana) si:** el proyecto es Mini/Chico (ver `.rocky-spec/reference/architectures.md`) o el usuario ya indicó que es un prototipo descartable — para esos casos alcanza con el Paso 1 (completitud), el resto es de más para algo que no va a vivir mucho tiempo. Preguntar si en duda: *"¿Hacemos la revisión completa de la spec (recomendado si esto va a producción) o solo el chequeo rápido de completitud?"*

#### Paso 1 — Completitud (mecánico, siempre se corre)

Buscar placeholders sin rellenar en todo lo generado — un `{{PLACEHOLDER}}` que sobrevivió es una promesa sin cumplir.

**Si `rocky` está disponible**, correr `rocky check qa .` — detecta también la sintaxis `{{NOMBRE, default: valor}}`, que el grep de abajo no cubre. **Si no está disponible**, aplicar el criterio manual:

```bash
grep -n "{{[A-Z_]*}}" SPEC.md SECURITY.md OBSERVABILITY.md CONSTITUTION.md design-system/MASTER.md 2>/dev/null
```

Cualquier resultado es un hallazgo 🔴 — significa que un paso anterior no completó lo que debía. Resolverlo ahí mismo (volver al paso correspondiente) antes de seguir, no dejarlo pasar.

#### Paso 2 — Ambigüedad (lente Analista Funcional)

Revisar `SPEC.md` (Features y User Stories) buscando adjetivos sin métrica que los acompañe: "rápido", "fácil de usar", "intuitivo", "robusto", "escalable", "simple", "moderno" — son opiniones, no requisitos. Un requisito real se puede verificar; un adjetivo suelto no.

Por cada uno encontrado, preguntar la versión medible:
> "La feature '{{feature}}' dice '{{adjetivo}}' — ¿qué la haría concretamente {{adjetivo}}? (ej. en vez de 'carga rápido', ¿'carga en menos de 2 segundos'?)"

Si el usuario no tiene un número concreto todavía, dejarlo explícito como pendiente en vez de fingir precisión: *"Sin objetivo numérico todavía — revisar antes del release"*, no inventar un número.

#### Paso 3 — Testabilidad (lente QA)

Para cada criterio de aceptación de `SPEC.md`, preguntarse: *¿alguien podría escribir un test que pase o falle según esto, sin tener que interpretarlo?*

| Criterio | ¿Testeable? |
|---|---|
| "El sistema debe ser seguro" | ❌ No — ¿seguro cómo? Reescribir como algo verificable (ej. "todas las passwords se hashean con bcrypt", que sí se puede testear) |
| "El login responde en menos de 300ms" | ✅ Sí — se puede medir y comparar |
| "La UI debe ser intuitiva" | ❌ No — subjetivo, no hay test posible |
| "Un usuario no puede ver pedidos de otro usuario" | ✅ Sí — se puede escribir un test de autorización |

Los criterios ❌ se reescriben ahí mismo con el usuario, o quedan marcados explícitamente como "criterio cualitativo, sin test automatizado — validar manualmente" si de verdad no hay forma de medirlo (ej. "el diseño se ve profesional" puede quedar como revisión manual, no todo tiene que convertirse en un número artificial).

#### Paso 4 — Trazabilidad inversa (mecánico)

**Si `rocky` está disponible**, `rocky check qa .` ya corre esto junto con la completitud del Paso 1 (`qa_review.check_traceability`) — incluye la corrección para menciones sueltas de un RNF fuera de su fila de definición (ej. en el Historial de cambios), que el bash de abajo no contempla. **Si no está disponible**, aplicar el criterio manual:

Verificar la cadena completa `RF-N → US-N → tarea`, y que los `RNF-N` con objetivo concreto tengan trabajo asociado:

```bash
# RF sin ninguna historia que lo implemente
for rf in $(grep -oE "RF-[0-9]+" SPEC.md | sort -u); do
  grep -q "implementa $rf" SPEC.md || echo "⚠️  $rf no tiene ninguna historia que lo implemente"
done

# Historias sin ninguna tarea asociada
for us in $(grep -oE "US-[0-9]+" SPEC.md | sort -u); do
  grep -rq "$us" TODO.md todos/ 2>/dev/null || echo "⚠️  $us no tiene ninguna tarea en el TODO"
done

# RNF con objetivo concreto (no el default) pero sin ninguna tarea que lo aborde
for rnf in $(grep -oE "RNF-[0-9]+" SPEC.md | sort -u); do
  # Agrupar TODAS las menciones de este RNF antes de decidir — si alguna
  # (típicamente la fila de definición) tiene el marcador de default, se
  # considera cubierto, aunque otra mención suelta (ej. una línea del
  # Historial de cambios que solo lista los IDs, tipo "RNF-1 a RNF-5") no lo
  # tenga. Evaluar línea por línea sin agrupar genera falsos positivos con
  # esas menciones sueltas — encontrado haciendo dogfooding de este mismo
  # chequeo sobre un proyecto real.
  if grep -F "$rnf" SPEC.md | grep -qiE "sin objetivo|sin proyección|sin política|un solo idioma|no aplica"; then
    continue
  fi
  grep -rq "$rnf" TODO.md todos/ 2>/dev/null || echo "⚠️  $rnf tiene un objetivo concreto pero ninguna tarea que lo aborde"
done
```

Una historia sin tareas es una promesa sin plan de trabajo — completar el TODO con lo que falta, o quitar la historia de `SPEC.md` si en realidad no se va a hacer en este MVP (y documentarlo en "Fuera del alcance"). Un `RF-N` sin ninguna historia es lo mismo un nivel más arriba — feature declarada pero nunca desglosada. Un `RNF-N` con objetivo real y sin tarea asociada es un requisito que suena bien en el papel pero nadie va a construir — o se agrega la tarea, o se ajusta el objetivo al default hasta que haya plan real de cumplirlo.

#### Paso 5 — Consistencia cruzada (lente Analista Funcional)

Chequear que los NFR de `SPEC.md` no contradigan las decisiones técnicas ya tomadas:
- ¿El NFR de escalabilidad es coherente con la arquitectura elegida en P4? (ver nota ya agregada en `.rocky-spec/commands/p4-architecture.md`)
- ¿El nivel de exigencia de `SECURITY.md`/`OBSERVABILITY.md` es coherente con "Retención de datos" y el tipo de datos que maneja el proyecto (ver `.rocky-spec/reference/security.md` "Nivel de exigencia")?

Si hay una discrepancia real (ej. NFR pide alta escala pero se eligió arquitectura Mini), avisar y preguntar cuál de las dos decisiones ajustar — no elegir en silencio.

#### Paso 6 — Casos borde (lente QA)

Para cada User Story crítica (P0), preguntar si están contemplados en el TODO o en los criterios de aceptación:
- **Caso vacío**: ¿qué pasa si no hay datos todavía? (lista vacía, usuario sin pedidos)
- **Caso de error**: ¿qué pasa si la acción falla? (red caída, validación fallida)
- **Caso límite**: ¿qué pasa en el borde? (el último ítem de una paginación, un valor en el máximo permitido)

No hace falta una tarea por cada combinación — alcanza con que quede una nota o tarea "Estados de loading/error/empty" ya presente (suele estar, ver `TODO.md.template` sección Frontend/UI). Si no está para una historia P0 crítica, agregarla.
