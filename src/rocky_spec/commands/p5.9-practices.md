> Referencia de **rocky-spec** — Paso P5.9 del flujo de creación: prácticas del proyecto (`PRACTICES.md`) — principios, patrones y herramientas derivados del stack, la arquitectura y el SPEC.

### P5.9 · Prácticas del proyecto

**Saltear si:** el proyecto es **creativo puro** (video, contenido, branding sin código): no hay dónde aplicar principios de código ni patrones.

**Versión mínima si:** la escala es Mini/Chico o el proyecto es un prototipo descartable. Se genera el mismo archivo pero solo con principios base (KISS, YAGNI, DRY, Clean Code), **sin patrones** y con las herramientas justas (linter, formatter, tests). `{{PRACTICES_MODE}}` = `mínima`.

Este paso **decide qué se aplica a ESTE proyecto**, no describe todo lo que existe: el catálogo completo ya vive en `.rocky-spec/reference/` (`solid.md`, `general-principles.md`, `design-patterns.md`, `best-practices-frontend.md`, `best-practices-backend.md`). Abrir solo lo que hace falta.

#### Paso 1 — Derivación automática (sin preguntar de más)

Con lo ya recolectado en pasos anteriores, derivar sin preguntar:

- **Stack** → de P3 (`{{FRONTEND}}`, `{{BACKEND}}`, testing, ORM). Define qué herramientas tienen sentido: no proponer ESLint en un proyecto Python.
- **Arquitectura** → de P4 (`{{ARCHITECTURE_NAME}}`). Si tiene ficha en `.rocky-spec/reference/architecture-styles/`, sus prácticas y señales de alarma alimentan lo que sigue.
- **Escala** → mismo dato de P5.6 (`{{SECURITY_SCALE}}`) — no volver a preguntar, la escala del proyecto es una sola.
- **Principios activos** → del perfil (`profile.md`, sección "Principios de código"; ver `.rocky-spec/reference/coding-principles.md`, "Cómo el usuario activa / desactiva"). SOLID solo cuenta si el proyecto es mediano o más (ver `solid.md`).
- **Patrones** → uno solo entra si **un requisito del SPEC lo pide**. Buscar la señal en el SPEC, no en el gusto:

| Señal en el SPEC / stack / arquitectura | Patrón que se considera |
|---|---|
| Persistencia con lógica de negocio propia | Repository + Dependency Injection |
| Servicio externo registrado en P3 (pagos, email, storage) | Adapter detrás de una interfaz |
| Una entidad de P1.7 con ciclo de vida de estados | State (tabla de transiciones) |
| Varios algoritmos intercambiables (métodos de pago, descuentos) | Strategy |
| Creación condicional con 3+ variantes | Factory Method |
| Flujos asíncronos, notificaciones o picos de carga | Observer / eventos (+ Outbox e idempotencia si hay broker) |
| Varios canales de entrada (API + CLI + cron) | Puertos y Adapters (Hexagonal) |
| "Agregar X sin tocar el núcleo" | Registry / Plugin |

  Anotar el RF-N o la decisión que lo pide. Un patrón sin requisito que lo respalde **no entra**.
- **Patrones descartados** → los que el estilo de arquitectura elegido suele traer y este proyecto **no** va a usar, con el porqué (ej. Microservicios: equipo de 1 persona). Evita que una sesión futura los reintroduzca "por costumbre".
- **Buenas prácticas por capa** → según qué tiene el proyecto: `best-practices-frontend.md` si hay interfaz, `best-practices-backend.md` si hay backend. Elegir las secciones que aplican (ej. idempotencia solo si hay pagos o creación de recursos con reintentos) y decir por qué.
- **Herramientas** → de las tablas "Herramientas típicas" de esos archivos, cruzadas con el stack de P3. Marcar las que ya están en el stack y las que son solo recomendación.

Si con esto ya hay suficiente, mostrar el resumen directamente (Paso 2) sin preguntar nada más.

#### Paso 3 — Aprobar el contenido de `PRACTICES.md`

Usar **`.rocky-spec/templates/PRACTICES.md.template`** como base. Mapeo de la pantalla del Paso 2 a los placeholders:

| Placeholder | Sale de |
|---|---|
| `{{PRACTICES_SCALE}}` | mismo valor que `{{SECURITY_SCALE}}` de P5.6 — es una sola escala para todo el proyecto |
| `{{PRACTICES_MODE}}` | `completa` o `mínima` (ver arriba) |
| `{{PRACTICES_PRINCIPLES}}` | tabla `Principio \| Cómo se aplica en este proyecto`, una fila por principio activo |
| `{{ACTIVE_PATTERNS}}` | **solo los nombres**, separados por coma (ej. `Repository, Adapter, Strategy`) — el **mismo valor** que P6 usa en `CONSTITUTION.md` y `AGENTS.md`, no volver a derivarlo allá |
| `{{PRACTICES_PATTERNS_TABLE}}` | tabla `Patrón \| Dónde se aplica \| Lo pide (RF-N / decisión)` |
| `{{PRACTICES_DISCARDED}}` | lista de patrones descartados con su motivo |
| `{{PRACTICES_LAYERS}}` | qué secciones de `best-practices-*.md` aplican y por qué |
| `{{PRACTICES_TOOLS}}` | tabla `Objetivo \| Herramienta \| Estado` (ya en el stack / recomendada) |

En la versión mínima, dejar `{{PRACTICES_PATTERNS_TABLE}}` y `{{PRACTICES_LAYERS}}` sin valor: el template ya trae su texto por defecto.

#### Paso 4 — Generar `PRACTICES.md`

Igual que `ACCESSIBILITY.md`, `PRACTICES.md` es un archivo aparte que no forma parte de los 10 archivos base de P6 — se genera acá mismo:

**Si `rocky` está disponible**, correr:
```bash
rocky build . --values <json-con-los-valores-de-arriba> --template PRACTICES.md.template --output PRACTICES.md
```

**Si no está disponible**, generarlo directamente con las herramientas de edición, con el mismo criterio de mapeo del Paso 3.

Avisar al usuario:
> "Dejé listo `PRACTICES.md` con los principios, patrones y herramientas que aplican a este proyecto y por qué. Es una guía para el agente y para el equipo: hoy ningún comando la verifica, así que se cumple al escribir y revisar código. Las herramientas están como recomendación — no instalé nada."

Los patrones de este archivo son la fuente de `{{ACTIVE_PATTERNS}}` que P6 escribe en `CONSTITUTION.md` (Artículo 5) y en `AGENTS.md` ("Patrones activos de este proyecto").
