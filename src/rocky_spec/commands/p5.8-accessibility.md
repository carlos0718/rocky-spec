### P5.8 · Accesibilidad

**Saltear si:** el proyecto no tiene interfaz visual (ej. una API pura, un script CLI, un worker sin UI). A diferencia de `SECURITY.md`/`OBSERVABILITY.md`, este paso no genera nada mínimo cuando no aplica — no tiene sentido un checklist de accesibilidad para algo sin pantalla.

Consultar `.rocky-spec/reference/ui-design-guidelines.md` sección "Reglas de accesibilidad — mínimo indispensable" para el detalle completo.

#### Paso 1 — Detección automática (sin preguntar de más)

Con lo ya recolectado en pasos anteriores, inferir sin preguntar:
- **¿Tiene interfaz visual?** → de P2/P3 (stack) y P4.5 (si se generó `design-system/MASTER.md`, seguro que sí)
- **Escala del proyecto** → mismo dato ya recolectado en P5.6 (Seguridad, `{{SECURITY_SCALE}}`) — no volver a preguntar, la escala del proyecto es una sola.

Si con esto ya hay suficiente, mostrar el resumen directamente (Paso 2) sin preguntar nada más.

#### Paso 2 — Confirmar decisiones (una sola pantalla)

```
Accesibilidad — resumen para este proyecto:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Idioma:              es (default)
Sistema de foco:     outline nativo del navegador (default)
Paleta verificada:   [sí, ya se chequeó contraste en P4.5 | no todavía]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
¿Vamos con esto? (1 = sí / 2 = ajustar algo)
```

Si en P4.5 ya se armó `design-system/MASTER.md` con una paleta concreta, ofrecer chequearla contra WCAG AA en este paso (ver `.rocky-spec/reference/ui-design-guidelines.md` sección "Pairs de contraste") en vez de dejarlo sin verificar.

#### Paso 3 — Aprobar el contenido de `ACCESSIBILITY.md`

Usar **`.rocky-spec/templates/ACCESSIBILITY.md.template`** como base. Mapeo de la pantalla del Paso 2 a los placeholders sin default inline en el template:

| Placeholder | Sale de |
|---|---|
| `{{ACCESSIBILITY_SCALE}}` | mismo valor que `{{SECURITY_SCALE}}` de P5.6 — es una sola escala para todo el proyecto, no volver a preguntar |
| `{{CONTRAST_VERIFIED}}` | "sí" si se chequeó la paleta en el Paso 2; "no" si quedó pendiente |

El resto de los ítems del checklist (`alt`, `lang`, `div` clickeable, botón solo-ícono, contraste hardcodeado) arrancan sin marcar — no asumidos como resueltos. Se pueden marcar más adelante corriendo `rocky check accessibility .` sobre el código ya escrito.

#### Paso 4 — Generar `ACCESSIBILITY.md`

A diferencia de `SECURITY.md`/`OBSERVABILITY.md` (que se escriben junto con el resto de archivos base en P6), `ACCESSIBILITY.md` es condicional — se genera acá mismo, igual que `design-system/MASTER.md` en P4.5:

**Si `rocky` está disponible**, correr:
```bash
rocky build . --values <json-con-los-valores-de-arriba> --template ACCESSIBILITY.md.template --output ACCESSIBILITY.md
```

**Si no está disponible**, generarlo directamente con las herramientas de edición, con el mismo criterio de mapeo del Paso 3.

Avisar al usuario:
> "Dejé listo `ACCESSIBILITY.md` con el checklist mínimo de accesibilidad. Corré `rocky check accessibility .` cuando quieras auditar el código que ya está escrito — no reemplaza probar con un lector de pantalla real, pero agarra los casos más comunes (alt, lang, contraste, botones sin texto)."
