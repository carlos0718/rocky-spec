> Referencia de **rocky-spec** — Paso P5.6 del flujo de creación: seguridad (`SECURITY.md`, dependency scanning, decisiones de auth/CORS/rate limiting).

### P5.6 · Seguridad

**Saltear si:** el proyecto no tiene backend ni maneja secrets de ningún tipo (ej. un sitio 100% estático sin integraciones). Igual generar `SECURITY.md` mínimo con la sección de reporte de vulnerabilidades — cuesta poco y cualquier repo real lo tiene.

Consultar `.rocky-spec/reference/security.md` para todos los valores recomendados y el detalle del OWASP Top 10 adaptado.

#### Paso 1 — Detección automática (sin preguntar de más)

Con lo ya recolectado en pasos anteriores, inferir sin preguntar:
- **¿Tiene backend?** → de P2/P3 (stack)
- **¿Tiene auth?** → de P1.7 (si el dominio menciona `User`/`Usuario` con login, o si el usuario mencionó "login"/"autenticación" en la descripción)
- **¿Maneja datos de usuarios?** → de P1.7 (si hay entidades con datos personales: email, dirección, pagos)
- **¿Va a producción?** → de P5.5 (si eligió una plataforma de deploy)

Si con esto ya hay suficiente para armar `SECURITY.md`, mostrar el resumen directamente (Paso 2) sin preguntar nada más.

#### Paso 2 — Confirmar decisiones (una sola pantalla, no un cuestionario largo)

```
Seguridad — resumen para este proyecto:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Escala:              [Prototipo/demo | Producto real | Datos sensibles]
Auth:                [JWT stateless | Sessions | OAuth | no aplica]
Hasheo de passwords: bcrypt (default)
CORS (prod):         [origin del frontend detectado, o "a definir"]
Rate limiting:       [endpoints de auth | API completa | no aplica]
Dependency scanning: Dependabot semanal (default)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
¿Vamos con esto? (1 = sí / 2 = ajustar algo / 3 = este proyecto maneja datos sensibles — subir el nivel)
```

**Si el usuario elige 3** (datos sensibles/regulados): marcar `{{HANDLES_SENSITIVE_DATA}}` = sí en el template, y agregar la advertencia de auditoría profesional con más énfasis en el resumen final de P8.

**Si el proyecto no tiene backend/auth**: mostrar una versión reducida (solo dependency scanning + no exponer secrets en el bundle del cliente) en vez de la pantalla completa.

#### Paso 3 — Aprobar el contenido de `SECURITY.md`

Usar **`.rocky-spec/templates/SECURITY.md.template`** como base. Mapeo de la pantalla del Paso 2 a los placeholders sin default inline en el template:

| Placeholder | Sale de |
|---|---|
| `{{SECURITY_SCALE}}` | "Escala" del Paso 2 |
| `{{HANDLES_USER_DATA}}` | "sí" si el proyecto tiene entidades con datos personales (ver P1.7); "no" si no |
| `{{HANDLES_SENSITIVE_DATA}}` | "sí" solo si el usuario eligió la opción 3 del Paso 2; "no" en cualquier otro caso |
| `{{AUTH_PATTERN}}` | "Auth" del Paso 2 |
| `{{CORS_ORIGIN}}` | dominio del frontend detectado en P5.5, o "a definir" si no hay deploy configurado todavía |
| `{{RATE_LIMITING_SCOPE}}` | "Rate limiting" del Paso 2 |
| `{{SECRETS_MANAGEMENT}}` | plataforma de deploy elegida en P5.5 (ej. "panel de Environment Variables de Render") |
| `{{PROD_SECRETS_LOCATION}}` | mismo valor que `{{SECRETS_MANAGEMENT}}`, no volver a preguntar |
| `{{IF_APPLIES}}` (en el checklist OWASP, A04 y A10) | dejar la marca de item si aplica al proyecto (ver `.rocky-spec/reference/security.md` "Reglas por tipo de proyecto"), o borrar la línea completa del checklist si no aplica en absoluto |

Además, marcar `[x]` en el checklist OWASP los ítems que ya quedan cubiertos por las decisiones tomadas (ej. si hay auth con JWT + bcrypt, A02 y A07 ya están marcados). Dejar sin marcar los que requieren trabajo del usuario más adelante (quedan también como tareas en el TODO, ver Paso 5).

Mostrar el resultado y guardar el contenido aprobado en `.skill-state.json` para usarlo en P6 — igual que `SPEC.md` (P1.7), el archivo se escribe físicamente recién ahí, junto con el resto de archivos base.

Primera línea del Historial de cambios: fecha de hoy, "Security policy inicial (P5.6)", commit donde se guardó (se completa en P6).

#### Paso 4 — Dependency scanning (si el proyecto usa GitHub)

Si el usuario ya configuró GitHub en P5/P5.5, generar `.github/dependabot.yml` con el agrupamiento de `.rocky-spec/reference/dependencies.md` (patches/minors agrupados, majors sin agrupar):

```yaml
version: 2
updates:
  - package-ecosystem: "{{npm|pip|cargo|gomod según el stack}}"
    directory: "/"
    schedule:
      interval: "weekly"
    groups:
      minor-and-patch:
        update-types: ["minor", "patch"]
```

Si el proyecto es fullstack con `frontend/` y `backend/` separados, generar una entrada por directorio.

#### Paso 5 — Agregar tareas de seguridad al TODO

Completar el placeholder `{{SECURITY_TODO_ITEMS}}` de la sección "Seguridad" en `TODO.md.template` con los ítems del checklist OWASP de `SECURITY.md` que quedaron sin marcar en el Paso 3 — así no se pierden, quedan como trabajo pendiente visible. Si todos los ítems aplicables quedaron marcados, dejar la sección con una sola línea: `- [x] Checklist de seguridad inicial completo — ver SECURITY.md`.

Avisar al usuario:
> "Dejé listo el contenido de `SECURITY.md` (se escribe junto con el resto de archivos base) con las decisiones de seguridad y un checklist OWASP adaptado a este proyecto. Los ítems pendientes van a quedar en el TODO. Configuré Dependabot para que te avise de dependencias vulnerables — vas a ver los PRs automáticos en GitHub."

**Si el usuario marcó datos sensibles/regulados en el Paso 2**, agregar además:
> "Como este proyecto maneja datos sensibles, este checklist es un piso, no un techo — antes de manejar datos reales de usuarios te recomiendo una auditoría de seguridad profesional."
