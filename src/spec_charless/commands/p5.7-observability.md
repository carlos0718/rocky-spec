### P5.7 · Observabilidad

**Saltear si:** el proyecto no tiene backend/proceso que corra en producción (ej. un script de una sola corrida, o un sitio 100% estático). Igual generar `OBSERVABILITY.md` mínimo con la sección de logging del lado del build si aplica — cuesta poco.

Consultar `.charless/reference/observability.md` para todos los valores recomendados y el detalle de cada pilar.

#### Paso 1 — Detección automática (sin preguntar de más)

Con lo ya recolectado en pasos anteriores, inferir sin preguntar:
- **¿Tiene backend/proceso persistente?** → de P2/P3 (stack)
- **¿Tiene DB?** → de P1.7 — si sí, el health check debe incluir un chequeo de conexión
- **¿Va a producción?** → de P5.5 (si eligió plataforma de deploy)
- **Escala del proyecto** → mismo dato ya recolectado en P5.6 (Seguridad, `{{SECURITY_SCALE}}`) — no volver a preguntar, la escala del proyecto es una sola.

Si con esto ya hay suficiente, mostrar el resumen directamente (Paso 2) sin preguntar nada más.

#### Paso 2 — Confirmar decisiones (una sola pantalla)

```
Observabilidad — resumen para este proyecto:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Error tracking:      Sentry (default)
Logging:             [pino | winston | structlog | slog | tracing, según stack]
Health check:        /health (chequea: server{{, DB si aplica}})
Uptime monitor:      [UptimeRobot | ninguno por ahora]
Métricas:            Dashboard nativo de la plataforma (default)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
¿Vamos con esto? (1 = sí / 2 = ajustar algo / 3 = sin nada de esto, es un prototipo)
```

**Si el usuario elige 3** (prototipo/demo): generar `OBSERVABILITY.md` mínimo (nivel "Prototipo/demo", sin tareas de setup) y saltar los Pasos 3-4 de código.

**Si el proyecto no tiene backend**: mostrar solo la parte de logging (si el build/proceso genera logs relevantes) y saltar error tracking/health check/uptime.

#### Paso 3 — Aprobar el contenido de `OBSERVABILITY.md`

Usar **`.charless/templates/OBSERVABILITY.md.template`** como base. Mapeo de la pantalla del Paso 2 a los placeholders sin default inline en el template:

| Placeholder | Sale de |
|---|---|
| `{{OBSERVABILITY_SCALE}}` | mismo valor que `{{SECURITY_SCALE}}` de P5.6 — es una sola escala para todo el proyecto, no volver a preguntar |
| `{{LOGGING_LIBRARY}}` | "Logging" del Paso 2 (según el stack — ver `.charless/reference/observability.md`) |
| `{{HEALTH_ENDPOINT_PATH}}` | "Health check" del Paso 2 (default `/health`) |
| `{{HEALTH_CHECKS_LIST}}` | qué chequea el endpoint — "server" solo, o "server, conexión a DB" si el proyecto tiene base de datos (ver P1.7) |

Guardar el contenido aprobado en `.skill-state.json` para usarlo en P6 — igual que `SPEC.md`/`SECURITY.md`, el archivo se escribe físicamente ahí junto con el resto de archivos base.

#### Paso 4 — Generar el código base (si el usuario no eligió modo 3)

- **Health check endpoint**: generar el código real (no solo documentarlo) en el archivo de rutas correspondiente al stack, con el patrón de `.charless/reference/observability.md` sección "Health check endpoint" — chequeando DB si el proyecto tiene una.
- **Logger**: instalar y configurar la librería elegida con un wrapper mínimo (`logger.info`/`logger.error`) para que el resto del código lo use desde el arranque, en vez de tener que migrar `console.log` después.
- **Error tracking**: dejar el `Sentry.init(...)` (o equivalente) ya armado, leyendo el DSN de una variable de entorno — agregar esa variable a `.env.example` (vacía) y a la lista de secrets de `SECURITY.md`.

#### Paso 5 — Agregar tareas pendientes al TODO

Completar el placeholder `{{OBSERVABILITY_TODO_ITEMS}}` de la sección "Observabilidad" en `TODO.md.template` (ver `.charless/commands/p6-p7-files-todo.md`) con lo que quedó pendiente de configurar manualmente (ej. "crear cuenta en Sentry y pegar el DSN real", "conectar UptimeRobot a la URL de producción una vez deployado"). Si no quedó nada pendiente (modo 3, prototipo), dejar una sola línea: `- [x] Sin tareas de observabilidad — proyecto marcado como prototipo`.

Avisar al usuario:
> "Dejé listo el health check en `{{HEALTH_ENDPOINT_PATH}}` y el logger configurado. `OBSERVABILITY.md` documenta las decisiones. Te quedan un par de pasos manuales en el TODO — crear la cuenta de Sentry y pegar el DSN real es lo único que no puedo hacer por vos."
